## 1. Назначение и границы документа

Документ отвечает на требования BE-001–BE-014 из переданного владельцем
`backend-developer-handoff.md` от 28.10.2026: что уже есть, как подключать готовое,
что ещё необходимо реализовать и какие решения нужны от владельца продукта.

**Это не заявление о закрытии всех 14 задач.** В этой поставке оформлен отчёт
по существующему коду. Не добавлены несуществующие платежи, SMS-интеграция,
отзывы, избранное или юридические документы.

Адрес разработки из исходного handoff:
`http://dev.mysub.kz/api/v1/mobile/`.
Swagger: `http://dev.mysub.kz/api/v1/mobile/docs/`.
OpenAPI: `http://dev.mysub.kz/api/v1/mobile/schema/`.

Адреса приведены для подключения, но доступность хоста, версия развёрнутого
сервера, CORS, HTTPS и доставка изображений в этой работе не проверялись.
Отчёт описывает код репозитория, а не подтверждённое состояние production.
Не нужен второй backend или отдельная клиентская база данных.

## 3. Уже выполненные изменения CRM и общего booking backend

Эти возможности уже реализованы; их не требуется создавать заново:

1. Доступность проверяет полный интервал услуги, график, перерывы,
   занятость и пересечения записей клиента. Интервал начала отделён от длительности.
2. В расписании сохраняется обозначение акции; отметки явки сохраняются.
   Поиск клиента доступен в кабинете, а отмены/неявки остаются в истории.
3. График специалиста можно выделять областью календаря; повторный клик
   снимает выбор даты.
4. Абонемент услуги имеет число посещений, режим цены и отдельные даты.
   Общий первый час заполняет остальные даты; ручные исключения сохраняются.
5. Независимая группа может быть пустой. Есть датированные занятия, добавление
   участников, индивидуальные отмены/переносы и отмена/перенос одного занятия.
   Перенос одного занятия не меняет весь будущий график.
6. Возврат из группы восстанавливает дату и выбранного специалиста/недельный вид.
7. Рестораны имеют столики с вместимостью, автоматическое назначение,
   подтверждение прихода, двухчасовые продления и завершение с полученной оплатой.
8. Ночная занятость видна в календаре обеих дат. Продление не создаёт новый
   заказ и не увеличивает оплату автоматически.
9. Группы запрещены для бизнеса ресторанов и салонов красоты; индивидуальные
   абонементы салонов сохранены. Для остальных бизнесов допустимость группы
   определяется категорией услуги, а не несвязанной основной категорией бизнеса.
10. Исправлена генерация UUID в браузерах без `crypto.randomUUID`.
    Ошибки подготовки/сохранения группы выводятся явно.

Исходники отдельного Flutter-приложения в отслеживаемой части этого репозитория
отсутствуют. Готовность перечисленного backend/CRM не означает, что Flutter UI
уже подключён ко всем новым возможностям.

## 4. Реальные мобильные операции

Пути таблицы относительны к `/api/v1/mobile/`.
Каталог и availability публичные; профиль и записи используют
`Authorization: Bearer <access_token>`.
Мобильная авторизация не использует CRM-заголовок `X-Partner-Email`.

| Метод | Путь | Основной результат |
|---|---|---|
| POST | `auth/send-code/` | 200: `message`, `expires_in`, `retry_after`; см. ограничения OTP ниже |
| POST | `auth/register/` | 201: `user`, `tokens`, `is_new_user: true` |
| POST | `auth/verify-code/` | 200: `user`, `tokens`, `is_new_user: false` |
| POST | `auth/refresh/` | 200: новый объект `tokens` |
| GET | `users/me/` | 200: текущий профиль |
| PATCH | `users/me/` | 200: обновлённый профиль |
| DELETE | `users/me/` | 204 без тела |
| POST | `users/me/avatar/` | multipart `file`; 200: `avatar_url` |
| GET | `cities/` | `data`: города с `id` и `name` |
| GET | `catalog/partners/` | `data`: партнёры |
| GET | `catalog/services/` | `data`: услуги |
| GET | `catalog/partners/{partner_id}/services/` | `data`: услуги партнёра |
| GET | `catalog/partners/{partner_id}/specialists/` | `data`: специалисты и их `service_ids` |
| GET | `catalog/partners/{partner_id}/specialists/{specialist_id}/availability/` | Слоты обычной услуги |
| GET | `catalog/partners/{partner_id}/availability/` | Слоты ресторана без выбора специалиста/столика |
| GET | `bookings/` | 200: `data` — история текущего клиента |
| POST | `bookings/` | 201: созданная запись; повтор абонемента может вернуть 200 |
| POST | `bookings/{booking_id}/cancel/` | 200: отменённая запись, включая повторный вызов |

`schema/` и `docs/` настроены отдельно в корневых URL.
Не следует вызывать придуманные мобильные методы отзывов, переноса,
избранного, уведомлений, оплаты или смены телефона: их нет в этой таблице.

### 4.1. Доступность и идентификаторы

Сначала получить партнёра, услугу и допустимых специалистов из каталога.
Проверять `service_ids`, а не совпадение названий.
Каталог услуги возвращает `id`, `partner_id`, `duration_minutes`,
`slot_interval_minutes`, `booking_mode`, `service_type`, `price`,
`is_pass`, `visit_count`, `pass_price_mode` и `image_url`.

Для обычной услуги запрос availability:

```text
GET catalog/partners/{partner_id}/specialists/{specialist_id}/availability/?date=YYYY-MM-DD&service_id={service_id}
```

Результат: `date`, `time_zone`, `duration_minutes`, `slot_interval_minutes`,
`slots` с точным временем `HH:MM`.
Выбирать время только из актуального ответа. Не округлять его к 30 минутам.
Сохранение повторно проверяет доступность: ранее показанный слот не гарантирует бронь.

Явный интервал услуги применяется в CRM и mobile. Для старого nullable
интервала сохранены прежние значения: CRM — 15 минут, mobile — 30 минут.
Редактирование другого поля услуги не меняет эту старую сетку автоматически.
Сетка привязана к местной полуночи; настроенные значения — делители 1440
в диапазоне 1–120 минут.

### 4.2. Обычная запись

Ниже только примеры формы JSON: IDs, UUID и даты не являются серверными
fixtures. Заменять их реальными значениями из каталога и availability.

```json
{
  "partner_id": 12,
  "specialist_id": 7,
  "service_id": 42,
  "starts_at": "2030-09-03T11:30:00+05:00"
}
```

Имя/телефон клиента берутся из авторизованного профиля. Пустое имя даёт
409 `PROFILE_INCOMPLETE`; чужие/неактивные связи и занятый слот отклоняются.
`comment`, `child_id`, параметры автомобиля, зала или номера не реализованы
как сохраняемые поля этого POST. Нельзя обещать клиенту их сохранение.
`visits` у не-абонемента отклоняется.

### 4.3. Ресторан

Для `booking_mode: "table"` не показывать выбор специалиста или столика.
Показывать услугу, дату, время и число гостей.
Список специалистов ресторана возвращается пустым намеренно.

```text
GET catalog/partners/{partner_id}/availability/?date=YYYY-MM-DD&service_id={service_id}&party_size=3
```

```json
{
  "partner_id": 12,
  "service_id": 42,
  "party_size": 3,
  "starts_at": "2030-09-03T11:30:00+05:00"
}
```

`party_size` — целое 1–1000. Сервер выбирает наименьший активный столик
достаточной вместимости, свободный на весь первоначальный двухчасовой интервал.
Ресторанные абонементы не поддерживаются.

`restaurant` в ответе содержит:

| Поле | Текущий runtime-тип |
|---|---|
| `table_id`, `table_capacity`, `party_size` | integer |
| `table_name`, `notice` | string |
| `ends_at`, `arrived_at`, `completed_at` | ISO datetime string или null |
| `paid_amount` | decimal string или null |
| `segments` | массив `{starts_at, ends_at, is_extension}` |

После подтверждения прихода менеджером статус `arrived` продлевается блоками
по два часа до `completed`. Не подтверждённая посадка автоматически не продлевается.
Worker проверяет просроченные интервалы каждые 30 секунд и догоняет пропуски
после перезапуска. При конфликте пытается переназначить следующую бронь;
иначе сохраняет предупреждения и блокирует конфликтующую посадку.

Полученная оплата записывается при завершении и не равна автоматически
каталожной цене. `segments` — интервалы одного визита, не отдельные оплаченные заказы.
Обычные часы работы ресторана как отдельная структурированная политика
в этом новом table-flow не реализованы; не объявлять их гарантией availability.

### 4.4. Абонемент услуги

```json
{
  "partner_id": 12,
  "specialist_id": 7,
  "service_id": 42,
  "starts_at": "2030-09-03T11:30:00+05:00",
  "visits": [
    "2030-09-03T11:30:00+05:00",
    "2030-09-05T11:30:00+05:00"
  ],
  "request_id": "a8754086-b878-44a4-9d9a-bc3b56860c7f"
}
```

Пример подходит только услуге с `visit_count: 2`.
Число дат должно точно совпадать с числом посещений услуги; предел входного
массива — 365. Даты сортируются; `starts_at` совпадает с наиболее ранней.
Один выбранный специалист используется для всех посещений.
Проверяются график, сетка, пересечения посещений, клиентская занятость и места.
Посещения сохраняются в общей транзакции.

Повтор того же UUID у того же партнёра с тем же нормализованным payload
возвращает существующее первое посещение с 200; первый успешный POST — 201.
Изменённый payload под тем же ключом даёт 409 `REQUEST_CONFLICT`.
Для обычных и ресторанных POST такая create-idempotency пока не реализована.
Срок хранения ключей не установлен опубликованным контрактом.

`booking_pass` сейчас nullable JSON, а не строго типизированный OpenAPI DTO.
Runtime-поля: `id` (UUID string), `group_id` (integer/null), `visit_number`,
`visit_count`, `price_mode`, `total_price`, `completed_visits`, `visits`.
Каждое посещение внутри содержит `id`, `visit_number`, `starts_at`, `status`.

В `per_visit` базовая сумма — цена услуги × число дат; в `total` — цена всего
абонемента. Базовая сумма распределяется по посещениям в целых копейках,
остаток достаётся первым посещениям. Скидки вычисляются сервером для дат/клиента.
`total_price` абонемента — базовая сумма: не считать её автоматически итогом
после скидок или полученной оплатой. Для сумм использовать записи соответствующих
visit IDs из `GET bookings/` и их `final_price`.

## 5. Статусы, деньги, история и отмена

Новый booking-код использует `booked`, `arrived` (ресторан), `completed`,
`cancelled`, `no_show`. В старых данных распознаются aliases:
`pending`, `записан`, `записана`; `canceled`, `отменен`, `отменена`;
`done`, `завершен`, `завершена`; `no-show`, `missed`, `неявка`.
Поле остаётся строкой; строгого общего OpenAPI enum и полного контракта
переходов для всех старых значений нет.

- Прошедшая дата сама по себе не подтверждает явку или завершение.
- `is_cancellable: false` тоже не доказывает завершение.
- Незнакомый статус не превращать в `completed` и не учитывать как посещение.
- Отмены/неявки скрыты в CRM-календаре, но остаются в истории.
- Один отсутствующий участник не удаляет занятие группы.

Текущая мобильная отмена допускается, пока `starts_at` строго больше серверного
времени и статус не закрыт. Проверка повторяется под блокировкой записи.
Повтор уже состоявшейся отмены возвращает 200, в том числе после наступления даты.
Чужой/не найденный ID даёт 404 `BOOKING_NOT_FOUND`.
Недопустимая отмена — 409 `BOOKING_CANNOT_BE_CANCELLED`.
Отдельные льготные cutoff/refund-правила подписок здесь не реализованы.

`base_price`, `discount_amount`, `final_price` — decimal strings.
Сервер использует точность 0.01 и `ROUND_HALF_UP`.
Не применять float для финансовых итогов и не пересчитывать сохранённую цену
по текущему каталогу. CRM показывает тенге; product-wide валюту и правила
возвратов следует утвердить явно, а не выводить только из UI.

`starts_at` выдаётся в серверном часовом поясе, сейчас Asia/Almaty (+05:00).
Другие timestamps могут иметь UTC offset. Парсить дату как instant с offset,
а не извлекать часы из строки. Месячные границы считать в согласованной зоне.
Отдельная timezone каждого партнёра и политика будущих timezone/DST изменений
не опубликованы.

`GET bookings/`: все подходящие записи клиента в tenant `public`,
порядок `starts_at DESC, id DESC`, без SQL limit и пагинации.
Текущая связь истории с клиентом использует его нормализованный телефон.
Смена/повторное использование номера и удаление аккаунта требуют отдельной
политики владения; нельзя считать её решённой только тестом двух разных номеров.

Readback обычной записи содержит `id`, `partner_id`, `partner_name`,
`service_name`, `specialist_name`, `starts_at`, `status`, три суммы,
`is_cancellable`, `created_at`, `booking_pass`, `restaurant`.
**Обычные `service_id`, `specialist_id`, `ends_at`/duration в этом DTO отсутствуют.**
Названия не заменяют стабильные IDs. Мобильные месячные/общие агрегаты отсутствуют.
Статистику возвратов, скидок и групп нельзя объявлять окончательно согласованной.

## 6. Профиль, вход, фото и ошибки

Профиль возвращает `id` как string, телефон, имя/email/avatar/city с возможным
null, язык, согласие/версию, детей, timestamps и `max_children: 2`.
`is_profile_complete` сейчас означает только заполненные имя и город.
Фото/email не участвуют в этом флаге; наличие URL не является верификацией личности.

PATCH сохраняет пропущенные поля. `children` — полная замена списка:
существующие дети передаются с их IDs, новые без ID; `[]` удаляет всех,
отсутствие свойства сохраняет список. Проверки чужих/повторных IDs есть.
Точную границу «младше 18», день рождения, 29 февраля и конкурентные замены
нужно довести до согласованной приёмки. Не обещать клиенту merge двух stale списков.
Согласие должно передаваться реальным boolean, не строкой; утверждённые версии
юридических документов эта поставка не предоставляет.

Avatar POST принимает multipart `file`, до 5 242 880 bytes и 25 млн pixels.
Изображение проверяется, EXIF-ориентация исправляется, размер уменьшается
до 1280×1280, результат сохраняется в WebP. При замене вызывается очистка старого
файла, но она обрабатывает только известный относительный URL-префикс.
Очистку после сохранения абсолютного `avatar_url` нельзя считать гарантированной.
Текущие ошибки обработки — 400 `INVALID_IMAGE`.
HEIC/HEIF, MIME-политика, multipart binary в опубликованной схеме,
доставка выданного URL в native/web, proxy/media routing и конкурентные
замены требуют отдельного подтверждения. Успех upload не доказывает доступность URL.

Вход пока разделён: register для нового номера, verify-code для существующего.
Send-code возвращает metadata, но в текущем обработчике не вызывает SMS-провайдера
и не создаёт production OTP challenge. Проверка сверяет код с тестовой настройкой.
Не считать expires/retry metadata доказательством реального expiry, single-use,
лимитов попыток и отправки SMS. Значение тестового кода и реальные test credentials
в этот документ намеренно не включены.

JWT-ответ: `access_token`, `refresh_token`, `token_type`, `expires_in`.
Refresh имеет серверную сессию и ротируется: после успеха сохранять оба новых
токена. Конкурентный refresh, reuse/revocation, multi-device и server logout
не объявляются полностью согласованными; logout endpoint отсутствует.
Автоматический единый new/existing phone-flow остаётся задачей BE-001.

Часть ошибок имеет форму:

```json
{
  "error": {
    "code": "SLOT_UNAVAILABLE",
    "message": "У специалиста уже есть запись на это время",
    "details": [
      {"field": "starts_at", "message": "У специалиста уже есть запись на это время"}
    ]
  }
}
```

Часть catalog/availability ошибок пока возвращает `{ "message": "..." }`.
Единый формат всех 400/401/404/409/422/429 и proxy-ошибок не завершён.
Транспортный сбой, не-JSON ответ или неуспешный HTTP нельзя превращать
в «пустая история», «нет свободных мест» или подтверждение операции.

## 7. Что не следует считать готовым

- Отзывы, favorites, notifications/push, verified phone change и checkout
  не подключать к выдуманным endpoint.
- Есть внутренние подписки, но нет готового мобильного коммерческого
  entitlement/payment-контракта. Не активировать льготы по факту открытия checkout.
- Есть независимые CRM-группы и защита мест, но mobile не публикует полный
  occurrence/teacher/seats/audience/child DTO. В `POST bookings/` нет отдельного
  `group_session_id`; нельзя из этого вывести все правила выбора занятия.
- Mobile POST принимает одну услугу. Медицинский визит с независимыми ordered
  entries, автомобиль/номер, зал/инвентарь, room/unit и booking comments
  ещё требуют согласованных моделей, API и тестов.
- CRM-переносы не являются клиентским mobile-reschedule. Нельзя использовать
  cancel-then-create вместо атомарного переноса.
- `DELETE users/me/` отзывает refresh-сессии и удаляет User, каскадом профиль,
  детей и связанные refresh records. Обработчик не задаёт завершённую политику
  будущих броней, платежей, медиа/аватаров, отзывов и повторной регистрации.
  401 после неопределённого ответа сам по себе не доказывает удаление.
- HTTPS, разрешённые Flutter web origins, media DNS и production OTP
  должны пройти серверную приёмку; локальные API-тесты её не заменяют.

## 8. Приёмка, зависимости и порядок работ

Последняя выполненная функциональная проверка версии выше:
163 Django-теста на изолированной SQLite, 28 frontend-тестов, production build
и type-check. PostgreSQL-only concurrency case исключён из SQLite-прогона.
PostgreSQL row-lock/concurrent acceptance и реальные native/web устройства
на опубликованном сервере ещё не сертифицированы.

В браузере с одноразовой БД проверены пустая группа, автозаполнение и исключения
времени, возврат к дате/специалисту, сохранение явки, table allocation,
продление worker, оплата, отмена с сохранением истории, ночная занятость,
сохранение старого интервала и Courses group при основной категории «Досуг».
Новые ресторанные формы/столики проверены на ширинах 360, 390, 600, 1440 px.
Это предыдущая проверка функционального кода, не повторный тест всех BE в этой
документационной поставке.

Готовые регрессионные fixtures/expected results находятся в
[mobile_api/tests.py](./mobile_api/tests.py),
[partner_api/test_groups.py](./partner_api/test_groups.py),
[partner_api/test_restaurants.py](./partner_api/test_restaurants.py) и
[partner_api/test_intervals.py](./partner_api/test_intervals.py).
Они создают изолированные данные и не являются обещанием наличия тех же IDs
или аккаунтов на dev-сервере.

Первый этап:

1. BE-001: выбрать единый phone-flow, SMS-провайдера и реальные OTP/session правила.
2. BE-003/BE-011: закрепить IDs/end/duration/status/error DTO; проверить HTTPS,
   CORS, media и профиль на согласованных native/web клиентах.
3. BE-006: утвердить формулы all-time/monthly visits/savings/refunds и выбрать
   вычисление по полной истории или серверные агрегаты.
4. BE-005: выбрать категории текущего выпуска, occurrence/attendee/resources,
   quotes и ordinary-create reconciliation. Затем закрывать BE-004/002/008/009/010.
5. BE-012/007/014: владелец утверждает support/FAQ/legal, состав платной
   подписки/провайдера оплаты, возвраты и политику удаления. Backend и Flutter
   реализуют согласованное, а не коммерческие условия из макета.

Backend возвращает по каждому BE точный метод/DTO, поведение повторов и конфликтов,
совместимость, ожидаемые ошибки и disposable acceptance данные.
Flutter подключает только подтверждённые методы и сообщает readback/transport
результаты. Номера для OTP, токены и credentials передавать отдельно по приватному
каналу; не добавлять их в документацию или Git. Для удаления использовать только
специально разрешённый одноразовый аккаунт, не обычного пользователя.

## 9. Обновление сервера

Production в этой работе не обновлялся. Команда для владельца сервера:

```bash
cd /opt/apps/mysub
git pull
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build
```

Проверить миграции, запуск `restaurant-renewals`, актуальную `schema/`,
наличие restaurant availability, доступность media и реальные клиентские сценарии.
Обновление этого MD само по себе не закрывает открытые BE-задачи и не меняет API.
